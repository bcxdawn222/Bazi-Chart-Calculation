# Proposal: android-apk-runtime-unpack

## Why

现有静态分析已确认 `base.apk` 的业务 DEX 被壳入口和尾随数据遮蔽，普通解压无法得到可读业务代码。需要通过可重复的 Android 运行时流程捕获实际加载的 DEX、资源和 native 证据，再恢复为可反编译源码。

## What

- 新增隔离工具检查与 AVD/ADB 运行时任务入口，记录样本哈希、设备 ABI、安装启动结果和完整日志 | verify: 使用现有 `Pixel_6` AVD 执行一次任务，生成 `manifest.json` 且失败状态可区分设备、安装、启动和 ABI 错误
- 新增运行时导出流程，收集进程映射、释放文件、运行时 DEX 和 native 加载证据 | verify: 对成功运行或明确阻塞的任务生成带大小、来源和 SHA-256 的 artifact 清单
- 新增 DEX/资源恢复流程，调用隔离的反编译工具并保留原始 dump、工具版本和失败项 | verify: 至少一个有效运行时 DEX 能产出可检索的反编译目录，或生成可复核的阻塞报告
- 新增 `libyiqilibrary.so` 与壳加载证据整理，关联 JNI 方法、URL/密钥接口和运行时加载位置 | verify: 报告能追溯每个关键结论到文件、偏移/符号或运行日志
- 新增端到端验证报告和重复执行说明，保留原始 APK 与静态报告不变 | verify: 重复执行不会修改输入 APK，报告中的样本哈希与输入一致

**Not in this change**: 不恢复原始开发工程、注释和构建配置；不处理真实账号、服务端鉴权或用户数据；不修改原始 APK，不做不可回滚的补丁；`base1.apk` 只作为对照样本，不纳入同一壳恢复链路。

## How

- 选择现有 `Pixel_6` AVD 作为第一运行目标，并把 ABI 检查作为显式前置条件；若 ARM native 无法加载，保留证据并转入静态壳数据分析。
- 运行时优先捕获真实加载的 DEX/映射/释放文件，再进入资源解码和 JADX/apktool 近似源码恢复；不以修改 APK 绕过校验作为默认路径。
- 新工具安装在项目隔离目录或 `.venv`，所有步骤由 `scripts/` 组织并写入 `logs/`；原始样本只读，任何副本补丁都必须记录原字节、新字节和适用范围。

## Risk

- ABI 风险：x86_64 AVD 可能加载不了 ARM native，任务会停在 `blocked_abi`；保留安装/启动日志，并不把空 dump 当作成功。
- 壳校验风险：重签或改包可能改变真实加载路径；默认只运行原样本，副本补丁只在证据证明必要时使用。
- 工具依赖风险：JADX/apktool/frida 版本差异会影响结果；清单记录工具版本，工具缺失时报告明确失败项。
- 网络与数据风险：应用可能访问自身服务；第一轮不依赖真实业务账号，日志只保存本地分析证据。
- 回滚计划：删除本变更新增的工具目录、运行时 artifact 和报告即可；原始 APK、已有静态报告和原始日志不覆盖。
