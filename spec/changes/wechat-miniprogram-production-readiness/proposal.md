# Proposal: wechat-miniprogram-production-readiness

## Why

当前版本已经具备核心排盘和红圈入口，但“功能存在”和“完整可交付”之间仍有明确差距：真实微信支付通知字段不兼容、发布包没有正式 API 地址、专家排班没有运营录入路径、支付后没有订单回查，合婚、每日运势和名号测算也没有完全达到 PRD 字段要求。本变更把这些缺口收敛为可验证的生产准备流程，同时保留没有商业化参数时的本地运行能力。

## What

- 修正微信支付 API v3 通知解析、商户与金额校验和幂等测试，使官方结构的成功通知能可靠更新订单 | verify: 使用外层 `id` 的固定通知样例调用完整通知处理后，订单变为 `paid`；重复通知不重复入账；AppID、商户号、金额或币种不匹配时拒绝更新
- 增加小程序显式运行配置和线上状态提示，移除发布版本对手工 Storage 注入 API 地址的依赖 | verify: 配置 HTTPS 地址时登录、配置、同步和订单请求使用该地址；未配置或地址非法时本地功能可用且线上功能显示明确原因
- 补齐专家、排班和订单运营管理接口及运营页面，使空数据库可以配置一个可购买的咨询服务 | verify: 通过受保护运营接口创建专家和排班后，小程序能读取并选择；无管理员令牌时所有写操作返回拒绝；运营页能查看订单但不能伪造支付成功
- 增加用户单笔订单查询、最近订单展示和支付后有限轮询，完成支付状态可见流程 | verify: 模拟通知延迟时页面从待确认更新为已支付；轮询达到上限后停止并保留手动刷新；用户不能读取他人订单
- 补齐每日运势、合婚和名号测算的 PRD 字段，并保持所有输出可解释、可测试 | verify: 每日运势固定输出五类字段；合婚接受地点、经度、真太阳时和子时口径并展示结构化分项；名号可选关联最近命盘且不生成喜用神结论
- 固定康熙笔画第三方来源版本和 MIT NOTICE，更新导入脚本元数据 | verify: 数据文件元数据包含仓库、提交 SHA、许可证和导入日期，交付包包含对应 NOTICE，固定样例“李明”为 7 画和 8 画
- 完善部署、测试、文档和交付脚本：安装依赖、支持 HTTPS 域名配置、更新 PRD/Phase、重新生成 Word 和交付包 | verify: 所有操作从 `scripts` 入口执行；本地测试、结构检查、部署配置渲染和交付生成通过；没有正式参数时报告外部终验阻塞而不宣称真实支付完成

**Not in this change**: 不实现 AI 解读、会员、深度付费报告、分佣、完整 CRM、完整大师履约后台或评价运营后台；不引入旧 APK 网络接口和密钥；不增加参考图未圈出的功能；不在缺少备案 HTTPS 域名、正式 AppID、商户参数和证书时执行或伪造真实扣款验收。

## How

- 按 `design.md` 的接口契约拆分支付通知、运营接口和页面状态，避免继续扩大单一后端入口文件和工具页。
- 支付解析构造强类型通知对象，外层通知 ID 与交易资源字段分别读取；数据库继续以通知 ID 幂等，以服务器订单金额为唯一价格依据。
- 新增运行配置模块；发布模式只接受显式 HTTPS 地址，开发模式允许可见的调试覆盖。没有地址时 API 层返回统一 `local-mode` 原因。
- 复用现有专家、排班和订单表，增加最小运营 CRUD、输入校验和历史引用保护；支付状态不开放给运营页面直接修改。
- 小程序支付后查询单笔订单，采用有上限的轮询并提供手动刷新和最近订单列表。
- 合婚、每日运势和名号结果保持传统文化研究与娱乐参考，规则依据和输入口径直接显示，不把简单五行计数包装成旺衰或喜用神。
- 部署脚本在重启服务前安装 `requirements.txt`，域名模式生成 HTTPS Caddy 配置；内部 HTTP 模式只用于服务器自检。

## Risk

- 正式支付仍依赖客户提供的微信支付主体、商户证书、API v3 Key、平台证书、备案域名和 HTTPS；代码完成不能替代真实交易终验。
- 新增运营 API 扩大了管理面，必须继续依赖强 `ADMIN_TOKEN`、限长校验和日志脱敏，且不能把令牌写入页面或交付文档。
- 合婚结构化分项会改变现有输出布局；专业规则尚无客户基准样例，因此只提供透明参考项并保留旧摘要。
- 部署脚本改动 Caddy 配置存在服务中断风险；继续执行配置验证，验证失败恢复备份且不重启代理。
- 工具页和运营页功能增加可能导致文件过大；实现阶段必须按领域拆分模块并保持页面兼容。
