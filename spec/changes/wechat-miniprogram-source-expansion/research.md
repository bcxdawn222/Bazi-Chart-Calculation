# Research: wechat-miniprogram-source-expansion

## Practices

- 恢复源码按“字段证据、规则证据、交互证据”分级使用：布局中的字段名称可证明产品展示过该字段，但只有可追溯规则表或计算链才能作为新算法依据。
- 现有原生微信小程序已经形成可运行基线，扩展应保持 `normalizeBirthInput -> bazi.calculate / ziwei.calculate -> format.buildResultViewModel` 调用链，新增细节放入独立模块，避免页面承担算法职责。
- 算法增强采用固定样例和边界样例双重验证；已有 599 组常规日期、55 组闰月及页面流程检查继续作为回归基线。

## Constraints

- `base1.apk` 恢复结果包含业务 Activity、XML、藏干设置、纳音和紫微展示证据，但 JADX 报告 7 个反编译错误；页面字段存在不等于计算规则完整，违反该约束会把展示占位误写成算法结果。
- `base.apk` 与 `base1.apk` 是不同应用，包名、服务地址和 native 结构均不同；规则必须逐字段核验，违反该约束会拼接出不存在的统一算法。
- 客户没有提供原始算法或权威结果集；五行旺衰、喜用神、格局、庙旺利陷等存在流派差异，缺少样例时只能实现有明确规则依据的部分。
- 当前真太阳时只有经度差乘四分钟的近似修正，参考文档要求加入均时差；修改会影响跨日、子时和四柱结果，必须保留修正明细和边界测试。
- 当前工程是纯前端本地计算，没有登录、订单、支付或 AI 后端；本次扩展不能把后续商业化需求混入本地算法改造。
- 动态语言文件应尽量不超过 300 行；`bazi.js` 与 `ziwei.js` 继续堆叠规则会降低可维护性，因此新增明细规则需要拆分模块。
- Run & Debug 必须通过 `scripts/check_miniprogram.py` 或对应 shell 入口执行，日志继续写入 `logs` 目录。

## Decided

- [DEC-1] 保留现有原生微信小程序和本地计算架构 | decided from status quo: 当前工程和回归脚本已经通过基础验收，替换框架会增加无关迁移风险。
- [DEC-2] `base1.apk` 作为八字、紫微字段和布局第一来源，`base.apk` 只补充真太阳时、喜用与解读入口证据 | decided from status quo: 两份 APK 属于不同产品，且 `base1.apk` 业务源码更完整。
- [DEC-3] 真太阳时升级为经度修正加均时差，并展示修正明细 | escalated | 参考文档明确要求均时差，当前实现仅为经度近似；if wrong: 会改变边界时刻四柱，撤销方式是保留旧经度算法并通过配置切回。
- [DEC-4] 当前扩展实现藏干、藏干十神、纳音、客观五行统计及可追溯的紫微星曜关系 | escalated | 这些字段有恢复布局或规则证据且属于参考文档核心范围；if wrong: 用户可见结果字段增加，撤销方式是移除详情模块和页面绑定，不影响基础四柱接口。
- [DEC-5] 旺衰、喜用神、八字格局、紫微格局和流月延后到客户样例驱动阶段 | escalated | 当前只确认到页面或结果对象线索，完整本地规则不足；if wrong: 当前版本字段少于参考文档完整 P0，获得规则后可在独立详情模块补入。
- [DEC-6] 结果页继续使用单页滚动分区 | auto | 与现有流程兼容且新增字段可按区块插入；reversibility: 后续可拆成分页或 Tab，不改变算法接口。
- [DEC-7] 支付、会员、AI 和咨询不进入本次 change | auto | 当前没有已确认后端契约或付费内容；reversibility: 后续建立独立跨前后端 change。
