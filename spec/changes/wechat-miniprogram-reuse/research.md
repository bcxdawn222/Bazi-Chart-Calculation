# Research: wechat-miniprogram-reuse

## Practices

- Android `Activity`、XML layout 和 Java 事件逻辑不能直接作为微信小程序工程运行，需要映射为页面 `.js`、`.wxml`、`.wxss` 和页面配置 `.json`。
- `base1.apk` 的恢复产物包含明确的八字和紫微业务页面，可作为第一来源：`BzInputActivity`、`BzTimeInput`、`BzPaiPanForm`、`BzShowForm`、`ZwView`、`ShiErGongView`，以及 `activity_bz_*`、`activity_zw_*` 布局。
- `base1.apk` 的源码存在 JADX 部分错误和混淆命名，适合提取字段、流程、页面结构和规则线索，不直接作为微信小程序源码编译。
- `base.apk` 已恢复出 `yiqi.bazi` 业务包和 WebView/AI/解读相关入口，但当前报告明确其源码是部分恢复结果，关键 native 算法未完整恢复；适合作为功能范围和交互参考。

## Constraints

- 当前项目没有微信小程序工程骨架、`app.json`、`project.config.json` 或页面代码，需要新建最小可导入工程。
- 客户没有提供现成算法或代码；首版排盘逻辑需要从恢复源码中提取可验证规则后，以小程序 JavaScript 重新实现。
- `base1.apk` 的网络接口和 `base.apk` 的旧 SOAP/加密接口均未作为本次前端改造的可靠依赖，避免直接把旧服务地址和密钥逻辑带入小程序。
- 微信小程序首版先覆盖客户已确认的八字、紫微、时间处理和结果展示范围；支付和 AI 大数据接入仍按 PRD 保留为后续确认项。
- 其他 APK 模块，如六爻、奇门、会员、收藏、文章、聊天和悬赏，不纳入本次改造。

## Decided

- DEC-1：首版先在小程序端完成本地核心排盘，不直接复用旧接口；依据是旧接口存在历史域名、SOAP/加密和服务端依赖，且缺少可确认的服务契约。该决定可逆，后续可增加适配层。
- DEC-2：首个可运行版本暂不实现支付和 AI 大数据；依据是客户尚未确认付费内容和 AI 接入范围，先保留页面扩展点。该决定可逆，后续不影响核心排盘页面。
- DEC-3：排盘结果采用单个可滚动结果页，按八字、紫微、运势和解读分区展示；依据是最接近已有 APK 的结果阅读流程，且比多页面路由更容易先验证字段。该决定可逆。
- DEC-4：以 `base1.apk` 恢复源码作为排盘字段和页面结构的第一参考，以 `base.apk` 的恢复源码作为功能范围和解读入口的第二参考；依据是 `base1.apk` 的八字/紫微类和布局证据更集中，而 `base.apk` 的关键算法仍有部分恢复状态。
